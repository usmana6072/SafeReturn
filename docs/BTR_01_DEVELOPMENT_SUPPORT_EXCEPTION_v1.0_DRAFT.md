## 6. Atomicity, replay, concurrency and failure contract

These are mandatory design requirements for the future restricted command, not an implemented SQL interface:

1. **Closed command:** fixed project/email/verified subject UUID/support role, exact executor human/UUID, amendment/packet/implementation digests, approval ID, expected absent active grant, expiry and explicit confirmation. Reject unknown fields/roles/targets/extra accounts. Scope cannot come from arbitrary client input. Pin the sole consumed approval across all idempotency keys so another key cannot authorize a second grant or regrant.
2. **Idempotency:** scope includes exact executor/project/operation/subject; hash canonical non-secret command including role, approval and expiry. Same key/body returns only the encrypted original receipt after current-authority checks; changed body conflicts. Revoked/expired authority cannot use replay to regain privileges or retrieve protected results. Completed receipts never extend grant expiry or reinsert a revoked role. Unknown outcome uses same-key reconciliation, never a new-key blind retry. Preserve a consumption tombstone beyond receipt expiry to prevent reuse; retention requires approval.
3. **Locking:** one bounded database transaction, existing global custody/lifecycle transaction-lock order then deterministic principal/exception/approval locks coordinated with existing writers; serialize the one-account approval consumption, expected state and active-role uniqueness. Recheck account/role/custody eligibility and current approval under locks. No fabricated revision column or count-as-version. Define exact authoritative snapshot/token and lock compatibility in the implementation design; no command may run until those choices are reviewed. Stale state or contention fails, never silently refreshes signed input. No network/provider call while holding database locks; validate short-lived provider evidence first and revalidate its bounded freshness/state under locks. Document residual provider revocation race and fail-closed admission/final checks.
4. **Atomic result:** insert exactly one historical support grant; bind its generated ID and enforced expiry to the consumed approval; insert minimal server-derived audit and encrypted idempotent receipt, all in the same commit. Any grant/constraint/expiry/consumption/audit/encryption/receipt/commit failure rolls back together. The external packet must already be durably archived and verified; no claim of a distributed transaction with Auth/email/archive. A failed grant may leave a separately created no-role Auth identity; report and clean up only by separately approved steps.
5. **Audit:** record verified actor, subject/grant, operation, change reference, prior/new state, timestamp and outcome. The complete requester/owner/executor/Ahmad mapping resides in the signed archive and approved command receipt; choose an unambiguous approved reference from existing audit fields. Existing safe_details allowlist is only from_status,to_status,reason_code,version,event_id,outcome. Do not invent fields, forged actor data or fictitious role versions. If existing columns cannot express linkage, require a separately reviewed additive migration. Application SQL/grants cannot suppress audit.
6. **Custody/fencing:** preserve all unrelated grants and security custodians. No bootstrap/last-custodian exception is created. Serialize with existing lifecycle changes; review current-role/session/job fences and next-command denial without mutating QR jobs or lifecycle records. Do not import broad lifecycle powers into this command.
7. **Errors:** CLI failures must be non-success with stable non-secret categories: identity/project mismatch, wrong target/role/executor, missing/expired/revoked approval, email/MFA/recent-auth denial, scope unavailable, stale/conflict/contention, dependency unavailable, and uncertain commit. BTR common API semantics remain unchanged; no new HTTP endpoint is created. No fallback credential, TLS downgrade, repair SQL or automatic retry with changed key.
