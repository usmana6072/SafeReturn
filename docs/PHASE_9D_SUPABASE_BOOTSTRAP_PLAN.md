## 2. JWT, HTTPS and MFA compatibility

`backend/app/core/auth.py:JWTVerifier` accepts only ES256 or RS256 public JWKS with kid/type/strength checks; validates exact issuer `<SAFERETURN_SUPABASE_URL>/auth/v1`, audience authenticated, role authenticated, sub/session_id, expiry and nonanonymous AAL claims. It rejects legacy HS256, refresh-token use, arbitrary key URLs and unverified staff role claims. The configured JWKS URL is exactly `/auth/v1/.well-known/jwks.json`. `backend/app/core/config.py:validate_auth_origin` requires an HTTPS origin with no path/credentials/query. No signing secret or provider service key may be used as a bearer substitute.

The self-hosted official asymmetric configuration documents ES256 through Auth signing keys and corresponding service JWKS. The bootstrap must verify actual public discovery output and issuer match SafeReturn; do not assume opaque API-key generation alone changes session-token signing. No private JWK, legacy shared key or service key may appear in the public JWKS/logs/report. [Official asymmetric Auth configuration](https://supabase.com/docs/guides/self-hosting/self-hosted-auth-keys).

HTTPS is a real local compatibility gate. Use the official HTTPS integration pattern with a loopback-only development certificate/CA, certificate SAN for the chosen local origin and explicit issuer/public URL routing. Do not use a public ACME challenge, expose80/443, accept a redirecting JWKS URL or disable certificate checks. [Official HTTPS/development certificate guidance](https://supabase.com/docs/guides/self-hosting/self-hosted-proxy-https).

Important repository-specific trust detail: JWTVerifier creates HTTPX with trust_env=False and no custom verify argument. Merely setting SSL_CERT_FILE or trusting a certificate in a browser does not prove this Python client trusts it. HTTPX normally uses certifi; a future isolated acceptance Python environment must have its actual default trust bundle reviewed and trust the approved local CA, with HTTPS/JWKS verification demonstrated and no verify=False or application-code shortcut. Keep certificate trust changes scoped to that test environment and explicitly approved; do not silently edit the production venv/system CA store. [HTTPX TLS behavior](https://www.python-httpx.org/advanced/ssl/).

Genuine MFA requires provider enrollment, challenge and verified code, then an actual elevated session/token. A signed synthetic aal2 token plus fabricated auth.sessions row remains only unit-test evidence. Enable TOTP enrollment/verification and real email confirmation explicitly; defaults are not acceptance guarantees. Local mail delivery/capture requires a separately approved fixture service/configuration; no production SMTP/SMS/OAuth provider. [Supabase TOTP flow](https://supabase.com/docs/guides/auth/auth-mfa/totp).
