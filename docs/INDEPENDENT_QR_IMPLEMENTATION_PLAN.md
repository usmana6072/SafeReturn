# Independent QR orders: implementation plan

## Approved contract

New products select exactly one QR type. The UI calls `ice` Emergency; stored `ice` values and existing scan URLs remain unchanged. Admin generates a selected type and identity quantity. One logical order item contains one product and one or more selected sizes/copy quantities. The default cart merge key is product ID; requesting another identity creates an explicit separate item key. Each verified item receives exactly one distinct QR, reused for every printed copy in every selected size.

Pricing follows v1.4: product `price_per_copy` in PKR, combined-copy limit, server-only calculation, immutable purchase snapshots. Variant prices are not authoritative. Payment evidence is private and never settlement proof. Public QR tokens never establish ownership. Existing pairs, profiles, order snapshots and frozen reprints retain their original semantics.

## First implementation: Phase 1

Files: `backend/app/db/models.py`, `backend/app/db/commerce.py`, additive `0037_independent_qr_foundation.py/.sql`, and focused offline schema tests. No historical migration is edited. Parent revision is `0036_product_copy_pricing`; installed revision is still unverified.

Identity shape: legacy QR has `pair_id` and no direct batch ID; standalone QR has a direct typed `batch_id` and no pair ID. Every standalone QR must have exactly one state row, enforced at commit. A state row cannot attach to a legacy QR. Public token and serial uniqueness remain global in `qr_codes`. New standalone replacement is deferred until an explicit custody/replacement workflow exists.

Legacy batches retain `generation_mode=legacy_pair`. Standalone batches require type and quantity. Provenance fields cannot be changed after generation. New product `qr_type` is nullable only for legacy/unconfigured products; Phase 3 makes it mandatory for new-model publication. No type is inferred from a legacy product.

`standalone_qr_states` is protected by RLS with no API/worker grants or policies in this phase. A deferred identity/state correspondence check makes direct insertion through old QR table privileges insufficient to mint a usable standalone QR. Owner readers remain unchanged. The anonymous projection receives an explicit legacy-pair filter while retaining its current profile/privacy projection; standalone public scan admission stays closed until Phase 7. Later phases add narrowly scoped helpers and reader compatibility before new admission.

Phase 1 does not claim PostgreSQL correctness based on SQLite tests. Offline tests exercise row checks/FKs against compiled model DDL and validate the migration chain; SQL functions, locks, deferred triggers, ACL/RLS and upgrade preservation require an isolated PostgreSQL rehearsal. Do not run the repository's shared database harness without an explicitly identified isolated target.

## Decisions retained for later affected phases

- Stock exhaustion after trusted payment: owner approved recording verified payment and holding the whole order for reconciliation, without partial allocation or automatic refund. A later authorized retry may allocate the entire order. Preserve financial truth independently of fulfillment state.
- Activation: owner approved confirmed delivery plus the purchaser's signed-in verified account. Gifting/transfers and concealed credentials are deferred. Public tokens never establish entitlement.
- Catalog: owner explicitly sets new product type and price. No inferred legacy backfill.
- Operations: provide approved bank/Raast instruction values and editor authority; define new single-QR physical QA and credential custody if applicable.
- Deployment/migrations: approve the concrete target and rehearsed migration/application procedure separately. No deployment or database application is part of Phase 1.
